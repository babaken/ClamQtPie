## 1. 確認事項の反映結果

| 項目 | 決定内容 |
|---|---|
| デスクトップ通知の実装方式 | Windows: PowerShell `ToastNotificationManager`を呼び出す方式／Linux: `notify-send`コマンドを呼び出す方式。抽象化ライブラリ（plyer等）は使用しない |

## 2. 通知トリガー一覧

config.jsonスキーマ定義書4.6節（notification）の各フラグに対応するトリガーを以下に定義する。

| トリガー | 発生元 | 対応config項目 | 通知チャネル |
|---|---|---|---|
| ウイルス検知 | オンデマンドスキャン／リアルタイム監視 | `on_detect_mail` / `on_detect_desktop` | メール／デスクトップ（両方独立してON/OFF可） |
| 定義更新失敗 | ClamAVService.update_database() / SchedulerServiceの定義更新ジョブ | `on_update_fail` | デスクトップのみ（メールは対象外、5章参照） |
| スケジュールジョブ失敗 | SchedulerService | `on_job_fail` | デスクトップのみ（メールは対象外、5章参照） |

### 2.1 メール通知の対象をウイルス検知のみに絞る理由

定義更新失敗・ジョブ失敗は頻度が読めず、メール送信失敗時にリトライしない方針（1章）と合わせるとメールボックスを圧迫する可能性があるため、初版ではメール通知はウイルス検知（重要度が高く即時性が求められる）のみに限定する。定義更新失敗・ジョブ失敗はデスクトップ通知＋ログ＋GUI（ホーム画面のステータス表示）で十分カバーできると判断する。

## 3. ウイルス検知通知の集約仕様

### 3.1 集約ウィンドウ方式

- `NotificationService`内に検知イベントを一時的に貯める`DetectionAggregator`を設ける
- 最初の検知イベント受信時に60秒のタイマーを開始し、以降60秒以内に受信した検知イベントはリストへ追加するのみで即時通知はしない
- タイマー満了時点で貯まった検知リストをまとめて1件の通知として送信する（デスクトップ／メール両方とも同一の集約ロジックを共有する）
- タイマー満了後、新たな検知イベントが来た場合は新しい集約ウィンドウ（新規タイマー）を開始する

### 3.2 集約対象の粒度

- リアルタイム監視・オンデマンドスキャンを問わず、集約ウィンドウは**アプリ全体で1つ**とする（スキャン種別ごとに分けない）。理由：一括スキャンで大量検知した場合とリアルタイムで連続検知した場合のどちらも、ユーザーへの通知は「まとめて1回」が望ましいため
- 誤って過度に通知が遅延しないよう、集約ウィンドウ中に検知件数が50件を超えた場合はその時点で即座に通知を確定させる（打ち切り閾値、config.jsonに`notification.max_batch_size`として追加、既定50）

### 3.3 タイムライン例

```text
t=0s    ファイルA検知 → 集約タイマー開始（60秒）
t=5s    ファイルB検知 → リストに追加（タイマーは継続、リセットしない）
t=40s   ファイルC検知 → リストに追加
t=60s   タイマー満了 → A/B/Cをまとめて1件の通知として送信
t=65s   ファイルD検知 → 新規タイマー開始（次の集約ウィンドウ）
```

（※デバウンス方式のWindowsリアルタイム監視詳細設計書5章とは異なり、本集約は「タイマーをリセットせず、最初の検知から60秒固定」とする点に注意。検知イベントの通知は多少の遅延を許容してでも一定時間内に必ず届ける方を優先するため）

## 4. デスクトップ通知

### 4.1 Windows実装

- PowerShellの`Windows.UI.Notifications.ToastNotificationManager`をサブプロセス経由で呼び出す
- 呼び出し方式: `subprocess`でPowerShellスクリプト（文字列）を`-Command`引数として実行、または一時`.ps1`ファイルを生成し実行する（生成方式は既存実装パターン踏襲）
- Toast内容:
  - タイトル: 「ウイルスを検知しました」（検知1件時）／「ウイルスを{n}件検知しました」（複数件時）
  - 本文: 検知1件時はファイル名＋ウイルス名。複数件時は先頭2件のファイル名＋「他{n-2}件」
  - アクション: クリックでメインウィンドウの隔離画面を開く（`activationType="foreground"`、アプリの実行パスに対して隔離画面への遷移引数を付与する方式を想定。Toastからのアクティベーション経路は別途アプリ起動制御と連携が必要）
- **検知内容（タイトル・本文）はPowerShellスクリプトに文字列として埋め込まず、環境変数（`CLAMQT_TOAST_TITLE`・`CLAMQT_TOAST_BODY`）で渡し、スクリプト側は`$env:`で読む。** 環境変数の値はコードとして解釈されないため、検知ファイル名に引用符等を含めても任意コードが実行されない（セキュリティレビューで発見・修正。Phase 11改訂。以前は`'`を`''`にエスケープするだけで、Unicodeの引用符（U+2019・U+2018）でエスケープを回避し任意コード実行が可能だった）

### 4.2 Linux実装

- `notify-send`コマンドを`subprocess.run()`で呼び出す
- 呼び出し例: `notify-send "ウイルスを検知しました" "ファイルA: Eicar-Test-Signature" --icon=<アプリアイコンパス> --urgency=critical`
- 複数件時のタイトル/本文は4.1節と同一ロジック（OS間で表示文言を共通化する）
- Linuxはクリックしてもアプリ側での特定画面遷移は標準では保証されない（`notify-send`はアクション付与に対応する通知デーモンとしない環境もあるため）。初版ではクリックアクションは実装せず、通知内容の表示のみとする

### 4.3 通知種別ごとの表示文言（検知以外）

| 種別 | タイトル | 本文 |
|---|---|---|
| 定義更新失敗 | 「定義データベースの更新に失敗しました」 | エラー概要（例: 「サーバーに接続できませんでした」）。詳細はログ画面へ誘導する文言を付す |
| ジョブ失敗 | 「スケジュールジョブが失敗しました」 | ジョブ名＋失敗理由概要 |

これらは検知通知と異なり集約対象外（3章の集約は検知通知のみに適用）とし、発生の都度通知する。

## 5. メール通知

### 5.1 送信条件

- `notification.on_detect_mail`がtrue、かつSMTP設定（config.jsonスキーマ定義書4.5節）が最低限入力されている（host, port, from_address, to_address, keyring経由のパスワードが取得できる）場合のみ送信を試行
- 未設定項目がある場合は送信自体をスキップし、ログにWARNING「SMTP未設定のためメール通知をスキップしました」を記録する（設定画面へのエラーダイアログは出さない。検知処理自体を止めないことを優先）

### 5.2 メール本文テンプレート

- 形式: プレーンテキスト（HTMLメールは初版では非対応）
- 件名: `[ClamAVフロントエンド] ウイルスを{n}件検知しました`（n=1件時も同一形式で統一）
- 本文テンプレート:

```text
以下のとおりウイルスを検知しました。

検知日時（最初の検知）: {first_detected_at}
検知件数: {count}件

--------------------------------
{各検知ごとに以下を繰り返し}
ファイル: {path}
ウイルス名: {virus_name}
検知日時: {detected_at}
--------------------------------

対応状況（隔離設定に応じて自動記載）:
{quarantine_status_summary}

本メールはClamAVフロントエンドから自動送信されています。
```

- `quarantine_status_summary`は、リアルタイム画面「検知時アクション設定」（画面設計書3章）が「自動隔離」の場合「該当ファイルは自動的に隔離されました」、「通知のみ」の場合「該当ファイルへの対応は行われていません。隔離画面から手動対応してください」を挿入する

### 5.2.1 TLS（証明書の検証）

- `smtp.encryption`が`ssl`の場合は`SMTP_SSL`、`starttls`の場合は`STARTTLS`でTLS接続する。いずれも`ssl.create_default_context()`で作った検証ありのコンテキストを使い、**サーバ証明書の正当性とホスト名の一致を検証する**。
- contextを渡さないと、Pythonの既定は検証なし（`CERT_NONE`・`check_hostname=False`）となり、中間者攻撃でSMTPの資格情報が盗まれ得る（セキュリティレビューで発見・修正）。
- 証明書の検証に失敗した場合は送信失敗（5.3節）として扱う（リトライしない。E7001）。

### 5.3 送信失敗時の挙動

- SMTP接続エラー・認証エラー等が発生した場合、**リトライは行わずログにERRORとして記録する**（1章の確認結果どおり）
- ログ記録内容: 送信対象（件数）、失敗理由（例外メッセージ）、失敗時刻
- ユーザーへは、次回検知時の通知が改めて試行される以外の救済導線は設けない（設定画面のSMTPタブに「テスト送信」ボタン（画面設計書8-2節で既出）があるため、ユーザー自身が設定を確認できる前提とする）
- 送信失敗によって検知そのものの記録（ログ・DB登録・隔離処理）が妨げられることはない（メール送信は他の処理と独立して実行し、失敗しても他処理へ影響させない）

## 6. 処理シーケンス（検知〜通知）

```text
ClamAVService/RealtimeManager: ウイルス検知
  → QuarantineService: （検知時アクション設定に応じ）隔離処理
  → Logger: 検知ログ記録
  → NotificationService.notify_detection(result)
       → DetectionAggregator.add(result)
            ├─ 初回検知: 60秒タイマー開始
            ├─ 2件目以降: リストに追加（3.2節の閾値チェックあり）
            └─ タイマー満了 or 閾値到達:
                 ├─ デスクトップ通知送信（4章）
                 └─ メール通知送信（5章、on_detect_mailがtrueの場合のみ）
```

## 9. Phase 11 改訂（実装で確定した仕様）

- 2章「ウイルス検知」の発生元にスケジュールスキャンを含める。スケジュールスキャンの検知は、リアルタイム監視の「検知時アクション」設定に従って隔離したうえで通知する（従来は検知結果を捨てており通知されていなかった）
- スケジュールジョブの定義更新が失敗した場合は「定義更新失敗」の通知のみを送り、「ジョブ失敗」の通知は送らない（二重通知の防止）。ジョブの最終実行結果は「失敗」と記録する
- 8章 未確定事項1: AppID「ClamAVFrontend」のままでもToastが通知センターに届くことをWindows 11実機で確認した
- 4.1節「クリックで隔離画面を開く」を実装した（`core/activation.py`）。AppUserModelIDの登録やCOMアクティベーションは使わず、次の方式とした
  1. 検知のToastに`activationType="protocol"`・`launch="clamqt:quarantine"`を付ける（定義更新失敗・ジョブ失敗のToastには付けない）
  2. URLスキーム`clamqt:`をアプリ起動時にユーザー単位のレジストリ`HKCU\Software\Classes\clamqt`へ登録する。クリック時は補助プログラム（配布版: 本体と同じフォルダの`ClamAVFrontendActivate.exe`、開発時: `pythonw.exe notify_activate.py`）が起動し、ユーザー単位のフォルダ`%LOCALAPPDATA%\clamav-frontend\show_request`へ固定の文字列`quarantine`を書いて終了する（一時ファイルに書いてから置き換える）。補助プログラムはウィンドウを持たず（console=False）、管理者権限も要求しない（asInvoker）。本アプリのexeは常に管理者権限で起動するため、exeを直接起動させるとクリックのたびにUACが表示されてしまうことからこの方式とした。当初はPowerShell（-WindowStyle Hidden）で書いていたが、クリック時にコンソールが一瞬表示されたため補助プログラムに変更した
  3. 起動中のアプリは同フォルダをQFileSystemWatcherで監視し、依頼を読んだら削除して隔離画面を表示する。書き込み中で読めない場合は200ms間隔で最大10回読み直す。アプリ起動前から残っていた依頼は破棄する
  - 安全性: 外部（ブラウザ等）から`clamqt:`を開かれても、書かれる内容は固定で、許可した画面名（`quarantine`）以外は無視する。URLの内容はコマンドラインに埋め込まない（コマンドインジェクションの防止）
  - 制約: アプリ停止中に通知をクリックしても画面は開かない。Linuxの`notify-send`は4.2節どおりクリック動作なし
  - Windows 11実機で、配布版exe（管理者権限で起動）に対し、通知（バナー・通知センター）のクリックで隔離画面へ切り替わり、ウィンドウやUACが表示されないことを確認した
  - アンインストール時はレジストリキー`HKCU\Software\Classes\clamqt`とフォルダ`%LOCALAPPDATA%\clamav-frontend`が残る（READMEのアンインストール手順に削除方法を記載）
- 検知・隔離はカテゴリ付きでログに記録する（6章「Logger: 検知ログ記録」を実装）
- 5章「対応状況」は、隔離設定ではなく実際に隔離できたかで記載する（コードレビューで修正。以前は設定値と最後の1件の値で決めており、隔離に失敗しても「自動的に隔離されました」と送っていた）
  - すべて隔離できた: 「該当ファイルは自動的に隔離されました」
  - 1件も隔離していない（失敗・通知のみの設定）: 「該当ファイルへの対応は行われていません。隔離画面から手動対応してください」
  - 一部だけ隔離できた: 「n件は自動的に隔離されました。残りのm件は隔離されていません（隔離に失敗したか、対応しない設定です）。ログを確認し、手動で対応してください」
  - リアルタイム監視は、隔離を試した後のシグナル`detection_handled(path, virus_name, quarantined)`で通知する（`detected`は検知した時点で、隔離の前に出る）
