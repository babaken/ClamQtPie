# Windowsリアルタイム監視 詳細設計書

対象モジュール: `core/realtime.py`（RealtimeManager、Windows実装部）
前提: 要件定義書2章「Windows: watchdog + ReadDirectoryChangesW」、詳細設計書RealtimeManagerクラス

------------------------------------------------------------------------

## 1. 確認事項の反映結果

| 項目 | 決定内容 |
|---|---|
| 監視対象の既定範囲 | 既定は「監視対象なし」。初回起動時（またはリアルタイム画面初回表示時）にユーザーへ監視対象パスの選択を促す。以降はリアルタイム画面から追加/削除できる |
| 監視イベント種別 | 作成（Created）・変更（Modified）・リネーム／移動（Moved、移動先のファイル）。削除（Deleted）は対象外（Phase 11改訂。11章） |
| デバウンス間隔 | 標準2秒（同一ファイルへの連続イベントを2秒間まとめてから最終スキャンを実行） |

------------------------------------------------------------------------

## 2. 全体構成

```text
RealtimeManager (core/realtime.py)
 ├─ WindowsWatcher（watchdogベース、本設計対象）
 │    ├─ Observer（watchdog.observers.Observer、内部でReadDirectoryChangesWを使用）
 │    ├─ EventHandler（FileSystemEventHandlerを継承）
 │    ├─ DebounceQueue（イベントの間引き・集約）
 │    └─ ScanDispatcher（ClamAVServiceへのスキャン依頼）
 └─ LinuxWatcher（clamonacc、別設計）
```

- `RealtimeManager`はOS判定により`WindowsWatcher`/`LinuxWatcher`のいずれかを内部に保持する（Strategyパターン）
- GUI（リアルタイム画面）からは`RealtimeManager.start()`/`stop()`/`set_enabled(bool)`のみを呼び出し、OS差異を意識しない

## 3. 監視対象の管理

### 3.1 初回起動時フロー

1. アプリ初回起動 かつ 監視対象パスが未設定（0件）の場合、リアルタイム画面初回表示時に案内ダイアログを表示
   - メッセージ例：「リアルタイム監視の対象フォルダが設定されていません。監視を開始するには対象フォルダを追加してください。」
   - ボタン：「今すぐ追加」（フォルダ選択ダイアログを開く）／「後で設定する」
2. 「後で設定する」を選んだ場合、リアルタイム監視は**OFF状態のまま**とし、対象0件の間はON操作自体を無効化（トグルをグレーアウトし、ツールチップで理由を表示）

### 3.2 監視対象パスのデータ管理

- 監視対象パスはconfig.jsonではなく、既存の`exclude`テーブルと対称的な位置付けのテーブルとしてSQLiteで管理する（複数パス・有効無効を持たせるため）

```sql
CREATE TABLE watch_target (
    id INTEGER PRIMARY KEY,
    path TEXT,
    enabled INTEGER,
    added_at TEXT
);
```

- リアルタイム画面（画面設計書3章）の「監視対象パス一覧」テーブルはこのテーブルを直接バインドする
- パス追加/削除/有効-無効切替は即座にテーブルへ反映し、`WindowsWatcher`が稼働中の場合は差分だけをObserverへ反映する（全体再起動はしない。3.3節参照）

### 3.3 監視対象の動的変更（稼働中の追加/削除）

- `Observer.schedule(handler, path, recursive=True)`のスケジュールをパス単位で個別管理し、`watch_target`の変更イベントを受けて該当パスのみ`schedule()`/`unschedule()`する
- 全パス停止→再起動という方式は行わない（他パスの監視が瞬断するため）

## 4. イベント監視の詳細

### 4.1 監視対象イベント

watchdogの`FileSystemEventHandler`のうち、以下のみを処理対象とする。

| watchdogイベント | 処理 |
|---|---|
| `on_created` | 対象とする |
| `on_modified` | 対象とする |
| `on_deleted` | 無視（要件により対象外） |
| `on_moved` | 移動先（`dest_path`）のファイルを対象とする（Phase 11改訂。フォルダの移動はwatchdogが中のファイルごとの移動イベントも発行するため、ファイルのイベントだけを扱う） |

- ディレクトリに対するイベント（`event.is_directory == True`）は無視し、ファイルイベントのみ処理する

### 4.2 除外リストとの照合タイミング

- イベント受信直後（デバウンスキューに積む前）に、リアルタイム画面の除外設定（ファイル／フォルダ／拡張子／プロセス、excludeテーブル）と照合する
- 除外判定に一致した場合はデバウンスキューに積まず破棄する（無駄なタイマー生成を避けるため、なるべく早い段階でフィルタする）
- 「プロセス」除外については、Windows環境ではファイルイベント単体からは書き込み元プロセスを特定できないため、初版では**ファイルパスベースの除外のみ**をリアルタイム監視に適用し、プロセス除外はオンデマンドスキャン等の別経路でのみ有効とする（この制約は非機能上の既知の制限として運用ドキュメントに明記する）

## 5. デバウンス処理

### 5.1 方式

- ファイルパスをキーとしたディクショナリ（`{path: Timer}`）でデバウンスを管理する
- イベント受信時：
  1. 既に同一パスのタイマーが存在する場合はキャンセルし、タイマーを2.0秒でリセットして再設定
  2. 存在しない場合は新規に2.0秒タイマーを設定
- タイマー満了時にそのパスを`ScanDispatcher`のキューへ投入する

### 5.2 タイムライン例

```text
t=0.0s  ファイルA 変更イベント検知 → 2.0秒タイマー開始
t=0.8s  ファイルA 変更イベント検知 → タイマーを再度2.0秒にリセット
t=2.8s  タイマー満了 → ファイルAをスキャン対象としてディスパッチ
```

### 5.3 大量ファイル同時変更時の考慮

- 多数のファイルが同時に作成・変更される場合（例：フォルダの一括コピー）、パスごとに独立したタイマーが生成されるため、2秒後に一斉にスキャンキューへ投入される可能性がある
- 6章のスキャンキュー・同時実行制御で吸収する

## 6. スキャンディスパッチとClamAVServiceとの連携

### 6.1 ScanDispatcher

- デバウンス満了後のパスを内部キュー（`queue.Queue`）に投入する
- ワーカースレッド（既定1〜2並列、プロトコル設計書5章`max_concurrent_connections`の範囲内で調整）がキューから取り出し、`ClamAVService.scan_file(path)`（clamdへは`SCAN`コマンド、プロトコル設計書2章）を呼び出す
- リアルタイム検知はオンデマンドスキャンより優先度を高く扱う（プロトコル設計書5章の方針に合わせ、リアルタイムキューを優先消費）

### 6.2 ファイルロック・アクセス不能時の扱い

- 書き込み中でファイルがロックされている、あるいはアクセス権限エラーとなる場合がある
- `scan_file()`呼び出し時に`ERROR`応答（プロトコル設計書3.1節）を受けた場合：
  1. 「ファイルアクセスエラー」として即座に諦めず、**1回だけ1秒後にリトライ**する
  2. 再度失敗した場合はログにWARNINGとして記録し、GUI通知は行わない（書き込み中の一時的なロックによる誤検知を抑制するため）

### 6.3 検知時の後続処理

- スキャン結果が`FOUND`の場合、リアルタイム画面の「検知時アクション設定」（画面設計書3章：自動隔離／通知のみ）に従い、`QuarantineService.quarantine()`またはNotificationServiceへ連携する
- 処理フローは詳細設計書「隔離」シーケンス図に準拠

## 7. スレッド・リソース管理

| 項目 | 方針 |
|---|---|
| Observerスレッド | watchdogが内部生成する監視スレッド（1つ、複数パスを一括管理） |
| デバウンスタイマー | パスごとに`threading.Timer`を使用。同時に存在しうる最大数はconfig上限（既定1000件）を設け、超過時は最古のタイマーを即時発火させてキューへ送る（メモリ枯渇防止） |
| スキャンワーカー | 固定スレッドプール（既定2、config.jsonで変更可） |
| 停止処理（`stop()`） | Observerの`stop()`＋`join()`、保留中タイマーの全キャンセル、キュー内未処理項目の破棄（停止時点で破棄する。再開時は新規イベント待ちとする） |

## 9. エラー・異常系

| 事象 | 検出 | 対応 |
|---|---|---|
| 監視対象パスが監視中に削除された（フォルダごと削除等） | watchdog内部で監視パス消失を検知（`OSError`等） | 当該パスの監視を停止し、`watch_target`テーブルの該当行を無効化（enabled=0）、GUI通知「監視対象フォルダが見つかりません」 |
| ReadDirectoryChangesWのバッファオーバーフロー（大量同時変更） | watchdog側で`OSError: [WinError 995]`等が発生しうる | 発生パスに対しObserverを再スケジュールし、ログにWARNING記録。ユーザー通知は行わない（頻発する場合のみ将来的にホーム画面へ警告表示を検討） |
| clamd未接続 | ScanDispatcherからの呼び出し失敗 | プロトコル設計書6章のエラー方針に従う（自動再起動試行等） |

## 11. Phase 11 改訂（実装で確定した仕様）

- Linux側（2章のLinuxWatcher）は「Linuxリアルタイム監視詳細設計書」（clamonacc連携）として作成した。方式の選択は`core/realtime_factory.py`で行い、Strategyパターンの代わりに同一インターフェースのクラス（RealtimeManager／ClamonaccRealtimeManager）を切り替える
- 10章 未確定事項1（watch_targetとUIの連動）: リアルタイム画面の監視対象パス一覧はwatch_targetテーブルを表示し、追加・削除・有効/無効切替を即時反映する（稼働中は差分のみ、3.3節どおり）
- 3.1節の初回フロー: 監視対象が1件も無い場合、リアルタイム画面の初回表示時（起動ごとに1回）に「今すぐ追加／後で設定する」の案内を表示し、有効な監視対象が無い間は開始ボタンを無効化してツールチップで理由を示す
- 6.1節「リアルタイム検知の優先」: オンデマンドスキャンが使える接続数を上限-1に制限し、リアルタイム用に1接続を常に残す（clamdソケット通信プロトコル設計書9.4節）
- 6.2節: リトライ後も失敗したファイルはE2004としてWARNINGログに記録する（GUI通知なし）
- 9章 E2002（バッファオーバーフロー）: watchdogライブラリがこの事象をアプリへ通知する手段を提供しないため、初版では未実装とする
- 7章のデバウンスタイマー上限到達はE2003としてDEBUGログに記録する
- 監視の開始/停止・検知・監視対象の消失（E2001、GUIにもダイアログ表示）はカテゴリ「リアルタイム」でログに記録する
- 4.1節 `on_moved`: 初版は「要件により対象外」としていたが、要件定義書に該当する記述は無く、一時ファイルに書いてから名前を変える保存方式（ブラウザのダウンロードの`.part`・`.crdownload`、アーカイブ展開後のフォルダ名変更等）で完成したファイルを検査していなかった（Linux実機で、名前変更後のEICARが検知されないことを確認）。移動先のファイルを検査対象とし、除外判定も移動先のパスで行う
- 4.2節: アプリ自身のフォルダ（`logs`・`quarantine`・`clamonacc`）は、除外リストに関係なく常に検査しない（clamonacc方式と同じ）。4.1節の`on_moved`対応後、隔離フォルダへの移動（隔離処理）が移動イベントとして検査され、隔離したファイルが再び検知されて隔離が無限に繰り返された（Linux実機で約2時間に7,500回）。あわせて`QuarantineService`は隔離フォルダ内のファイルの隔離を拒否する（QuarantineWriteError、E3001）
- 6.2節: スキャン時にファイルが既に無い（一時ファイルが削除・移動された）場合は、リトライもE2004の記録も行わない（DEBUGログのみ）。移動先は移動イベントで検査される。以前はclamdが読めないフォルダでは「Permission denied」のE2004が大量に記録されていた
