# clamdソケット通信 プロトコル設計書

対象モジュール: `core/clamav_service.py`（ClamAVService）
前提: 要件定義書 1章「clamdデーモンへソケット接続する方式を採用」に準拠

------------------------------------------------------------------------

## 1. 接続方式

### 1.1 接続種別の切替

| OS | 接続方式 | 接続先 |
|---|---|---|
| Linux | UNIXドメインソケット | `clamd.conf`の`LocalSocket`（例: `/var/run/clamav/clamd.ctl`） |
| Windows | TCPソケット | `clamd.conf`の`TCPSocket`/`TCPAddr`（例: `127.0.0.1:3310`） |

- 接続方式はOS判定（`platform.system()`）で自動切替し、config.jsonでの明示上書きも可能とする
- config.json対応キー（設定画面「詳細」相当、8章に追記予定）

```json
{
  "clamd": {
    "connection_type": "auto",   // auto | unix | tcp
    "unix_socket_path": "/var/run/clamav/clamd.ctl",
    "tcp_host": "127.0.0.1",
    "tcp_port": 3310,
    "connect_timeout_sec": 5,
    "read_timeout_sec": 30,
    "instream_chunk_size": 8192,
    "max_stream_size_mb": 100
  }
}
```

### 1.2 接続ライフサイクル

- コマンドごとに接続→送信→受信→切断の**都度接続方式**を基本とする（clamdはコマンド単位でのソケット処理を前提とした設計のため）
- 例外: `IDSESSION`を用いた複数コマンドの一括処理は初版では採用しない（保留機能同様、将来拡張）
- リアルタイム監視時の連続スキャンも、ファイル検知イベントごとに新規接続する（コネクションプーリングは行わない。理由: clamd側の同時接続数上限に依存させないため）

## 2. コマンド一覧と対応

clamdの標準コマンドセットのうち、本アプリで使用するものを以下に定義する。すべて`n`終端（`\n`）または`z`終端（NULL終端、応答をNULL区切りで受け取る）のどちらかを選択できるが、**本設計では`z`終端（NULLセーフ）を全コマンドで統一使用する**。

| コマンド送信文字列 | 対応メソッド | 概要 |
|---|---|---|
| `zPING\0` | `ping()` | 疎通確認。応答`PONG` |
| `zVERSION\0` | `get_version()` | clamd/エンジンバージョン取得 |
| `zRELOAD\0` | 内部利用（更新後の反映） | 定義DB再読込 |
| `zSCAN <path>\0` | `scan_file(path)`（clamdからアクセス可能なローカルパス時） | サーバ側ファイルパス指定スキャン |
| `zCONTSCAN <path>\0` | 未使用（初版） | エラー時も継続する一括スキャン |
| `zMULTISCAN <path>\0` | `scan_directory(path, recursive=True)` | マルチスレッドでのディレクトリスキャン |
| `zINSTREAM\0` + チャンク送信 | `scan_file(path)`（クライアント権限でしかアクセスできない/リモート想定パス時、および将来のリモート隔離連携） | ストリームスキャン |
| `zFILDES\0` + ファイルディスクリプタ（SCM_RIGHTS） | `scan_file(path)`（UNIXソケット接続時。Phase 11改訂、9.6節） | クライアントが開いたファイルをclamdが直接読むスキャン |
| `zSTATS\0` | 未使用（初版、ホーム画面の拡張候補） | プールスレッド等の統計情報 |
| `zSHUTDOWN\0` | 使用しない | clamdごと停止するため本アプリでは非対応 |

### 2.1 SCAN / MULTISCAN 使い分けの方針

- `scan_file()`: 単一ファイル指定時は`SCAN`を使用
- `scan_directory()`: ディレクトリ指定時は`MULTISCAN`を使用（clamd側の`MaxThreads`設定に従い並列スキャンされる）
- **前提条件**: `SCAN`/`MULTISCAN`はclamdプロセスから見えるローカルパスである必要がある。Windowsでtaskトレイアプリとclamdが同一マシン上にある構成を前提とするため通常は問題ないが、UNC パスやネットワークドライブ指定時は`INSTREAM`にフォールバックする（3.3節参照）

## 3. 応答フォーマットの解析

### 3.1 SCAN / MULTISCAN 応答

```
<path>: <SignatureName> FOUND
<path>: OK
<path>: <ErrorMessage> ERROR
```

- MULTISCANの場合、ファイル数分の行が返却される（末尾は`z`終端によりNULL区切り）
- パース方針: 各行を正規表現 `^(.*): (.+) (FOUND|OK|ERROR)$` で分解し、以下の内部構造体にマッピング

```json
{
  "path": "string",
  "status": "FOUND | OK | ERROR",
  "detail": "string (ウイルス名 or エラー内容、OKの場合は空)"
}
```

### 3.2 PING応答
`PONG` の1行のみ。タイムアウトまたは接続失敗時は「clamd未起動」と判定しエラー方針（詳細設計書4章）に従いGUI通知＋再起動試行を行う。

### 3.3 INSTREAM プロトコル詳細

1. `zINSTREAM\0` を送信
2. ファイルをチャンク単位（config `instream_chunk_size`、既定8192バイト）で読み込み、各チャンクを以下の形式で送信
   - 4バイト（ビッグエンディアン符号なし32bit整数）= チャンク長
   - チャンク本体（バイナリ）
3. 送信完了後、**長さ0のチャンク**（4バイトの`0x00000000`）を送信してストリーム終端を通知
4. clamdからの応答（SCAN応答と同一フォーマット、pathは`stream`固定文字列）を受信
5. `max_stream_size_mb`超過時はクライアント側で送信を中断し、`StreamMaxLength exceeded`エラーとして扱う（clamd.confの`StreamMaxLength`と整合させること。運用手順書側で値の同期を明記する想定）

### 3.4 VERSION応答
`ClamAV 1.x.x/dddd/Mon DD HH:MM:SS YYYY` 形式の1行。パースして`get_version()`（clamdエンジン部）と`get_database_version()`（定義DB日時部）に分離する。

## 4. タイムアウト・リトライ方針

| 項目 | 既定値 | 説明 |
|---|---|---|
| 接続タイムアウト | 5秒 | ソケット確立まで |
| 読み取りタイムアウト | 30秒 | PING/VERSION等の軽量コマンド |
| スキャン系読み取りタイムアウト | なし（無制限、ただし進捗コールバックで生存確認） | 大容量スキャンは長時間化するため固定タイムアウトを設けない。代わりに一定間隔（10秒）で無応答が続く場合はGUI側に「応答待ち」を表示し、ユーザーによる明示キャンセルのみで中断する |
| PING失敗時のリトライ | 3回、1秒間隔 | 3回失敗で「clamd未起動」と判定 |
| clamd自動再起動試行 | 1回のみ | `start_clamd()`実行後、5秒待って再度PING。失敗時はエラーダイアログを表示し自動リトライはしない（無限ループ防止） |

## 5. 同時実行制御

- リアルタイム監視によるスキャン要求とオンデマンドスキャン（スキャン画面からの実行）が同時に発生しうるため、`ClamAVService`内部にキューを設け、clamd側`MaxThreads`を超えない範囲で同時接続数を制御する
- config.json対応キー案: `clamd.max_concurrent_connections`（既定4）
- キュー超過時はリアルタイム検知を優先し、オンデマンドスキャンはキュー待機（進捗バーに「待機中」ステータスを表示）

------------------------------------------------------------------------

## 6. エラーハンドリング（本プロトコル層固有分）

詳細設計書4章「エラー方針」を以下の通り具体化する。

| 事象 | 検出方法 | ハンドリング |
|---|---|---|
| ソケット接続不可（ECONNREFUSED等） | `socket.connect()`例外 | 「clamd未起動」としてホーム画面ステータス更新＋自動再起動試行（4章参照） |
| 読み取りタイムアウト | `socket.settimeout()`超過 | コマンド種別に応じたリトライ or ユーザーへの中断可否確認 |
| 応答フォーマット不正 | 正規表現マッチ失敗 | ログにWARNINGとして生応答を記録し、当該行は「不明な結果」としてGUI表示 |
| INSTREAM時のサイズ超過 | クライアント側送信量カウント | 送信中断し`ERROR: StreamMaxLength exceeded`相当をGUIへ返す |
| ソケット権限エラー（Linux、Unixソケットのパーミッション） | `PermissionError` | 「権限不足」エラーダイアログ（詳細設計書のエラー方針に既定） |

## 7. 内部インターフェース（ClamAVServiceとの対応）

```text
ClamdClient（新規: core/clamd_client.py 相当を想定）
  - connect() -> socket
  - ping() -> bool
  - get_version() -> (engine_version, db_version, db_date)
  - scan_path(path, multi=False) -> list[ScanResult]
  - scan_stream(file_obj) -> ScanResult
  - reload() -> bool

ScanResult（データクラス）
  - path: str
  - status: Literal["OK", "FOUND", "ERROR"]
  - detail: str
```

`ClamAVService`は`ClamdClient`を内部に保持し、`scan_file()`/`scan_directory()`から呼び出す形とする（プロトコル層とサービス層を分離し、将来的なclamdバージョン差異やプロトコル拡張に備える）。

## 9. Phase 11 改訂（実装で確定した仕様）

### 9.1 オンデマンドスキャンのコマンド
- スキャン画面・スケジュールスキャンはディレクトリ内のファイルを列挙し、1ファイルずつ`SCAN`する（2.1節のMULTISCANは使わない）。MULTISCANは全件完了まで応答が無く、画面設計書2章の「現在スキャン中のファイル」「検知の逐次反映」を満たせないため（Phase 4の判断を本書へ反映）。`scan_directory()`（MULTISCAN）はClamAVServiceに残す
- 除外ルールはスキャン開始時に1回だけ読み込んで照合する（ファイルごとにDBを読まない）

### 9.2 SCANの権限エラー時のINSTREAMフォールバック（2章・8章未確定事項3/4の具体化）
- `SCAN`はclamdプロセス（Linuxでは通常clamavユーザー）がファイルを開くため、0700/0750のホームディレクトリ配下等は`Permission denied. ERROR`／`Access denied. ERROR`になる
- この応答の場合はアプリ自身がファイルを開き、`INSTREAM`で内容を送り直す。アプリも読めない場合は元のERRORを返す。`max_stream_size_mb`超過はファイル単位のERROR結果とする（一括スキャンを例外で中断しない）
- Linux実機（Ubuntu、ホームは既定0750）で、これが無いとユーザーファイルのスキャンがほぼ全てERRORになることを確認した

### 9.3 タイムアウト（4章）
- 読み取りタイムアウト（`read_timeout_sec`）はPING/VERSION/RELOAD等の軽量コマンドのみに適用し、`SCAN`/`MULTISCAN`/`INSTREAM`の結果待ちは無制限とした（4章「スキャン系読み取りタイムアウト: なし」どおり）
- 1ファイルの応答待ちが10秒以上続くと、スキャン画面の状態欄に「応答待ち（n秒）: ファイル名」を表示する（1秒ごとに経過秒を更新、ツールチップでフルパス）。応答が返ったら「スキャン中」に戻す（ScanWorkerの監視スレッド、`activity`シグナル）
- 「停止」を押すと、応答待ち中の通信を別スレッドから打ち切って直ちに中断する（`ClamdClient.abort_thread()`。スレッドごとに通信中のソケットを管理）。打ち切りによる通信エラーはエラー表示しない（4章「ユーザーによる明示キャンセルのみで中断」）
- clamdに接続できない場合（ClamdConnectionError）はスキャンをその時点で中断し、エラーを1回だけ通知する（ファイル数分のエラーを出さない）

### 9.4 同時実行制御（5章）
- `max_concurrent_connections`の上限をリアルタイム監視とオンデマンドで共有し、オンデマンド（スキャン画面・スケジュール）は上限-1までに制限してリアルタイム用の接続を常に1つ残す（`ClamAVService.scan_file(priority=True)`）
- オンデマンドスキャンが接続枠の空きを待つ間は、スキャン画面の状態欄に「待機中（リアルタイム監視のスキャンを優先しています）」を表示し、空いたら「スキャン中」に戻す。待機中も「停止」で中断できる（0.5秒ごとに停止要求を確認）。応答待ちの計測は接続枠を確保して通信を始めた時点から行う（待機時間を応答待ちに含めない）

### 9.5 clamdの起動（4章・8章未確定事項2の決定）
- clamdはOSのサービスとして起動する（アプリからclamdプロセスを直接起動しない）。`core/clamd_process.py`の`ClamdServiceController`
  - Windows: `sc start <service_name>`（既定「clamd」。本アプリは管理者権限で動作）。「既に開始されています」（1056）は成功扱い
  - Linux: `systemctl start <service_name>`（既定「clamav-daemon」。一般ユーザー時は`pkexec`で認証）
- `ClamAVService.ensure_available()`（PING 3回→サービス起動→5秒後にPING、失敗時E1006）をバックグラウンドで実行する（`ClamdStarter`）
- 起動の契機: 「ClamAV エンジン サービス」画面の「サービスを開始」ボタン（失敗時はエラーダイアログ。画面レイアウトの刷新でホーム画面の「起動」ボタンから移した）、および定期確認でclamdの停止を検知した時（`clamd.auto_start`、停止ごとに1回だけ。失敗時はトレイの吹き出し通知）
- 停止: 「ClamAV エンジン サービス」画面の「サービスを停止」（`ClamdServiceController.stop()`。Windows: `sc stop`、Linux: `pkexec systemctl stop`、失敗時E8003）
- 利用者が停止したclamdは、停止検知時の自動起動で起動し直さない。抑止は停止を要求した時点で始め（停止処理中に定期確認のPINGが失敗しても自動起動しない）、停止に失敗した場合は要求前の状態に戻す。抑止の解除は「サービスを開始」で手動起動したときだけ
- 定期確認（60秒ごと）のPINGはリトライなし・失敗をログに記録しない（clamd停止中にログが埋まるのを避けるため）。リトライ付きPINGの失敗のみE1001を記録する

### 9.6 UNIXソケット接続時のFILDES（ファイルディスクリプタ渡し）
- 9.2節の方式では、0700/0750のホームディレクトリ配下のファイルごとに`SCAN`（権限エラー）→`INSTREAM`と2回通信し、clamd.logに`File path check failure`の警告が毎回記録されていた。また`INSTREAM`は`max_stream_size_mb`（既定100MB）を超えるファイルを検査できなかった（Arch Linux実機で発見）
- UNIXソケット接続（Linuxの既定）では、アプリがファイルを開き、`zFILDES\0`に続けて1バイトのデータとファイルディスクリプタ（SCM_RIGHTS、Pythonの`socket.send_fds`）を送る。clamdはそのディスクリプタを直接読んで検査し、`fd[N]: OK`／`fd[N]: <ウイルス名> FOUND`を返す。パスは元のファイルのパスに読み替える（`ClamdClient.scan_fd()`）
- 名前付きパイプ等で待たされないよう`O_NONBLOCK`で開き、通常のファイルだけを渡す。シンボリックリンク（`O_NOFOLLOW`）・通常のファイル以外・アプリ自身が開けないファイルは、従来どおり`SCAN`（9.2節）。開く時点でファイルが無い場合は「ファイルが見つかりません（スキャンの前に削除または移動されました）」のERROR
- clamdがFILDESに非対応の応答（`UNKNOWN COMMAND`等）を返した場合は、WARNINGログを1回記録し、以降は`SCAN`（9.2節）に戻す
- Windows・TCP接続はファイルディスクリプタを渡せないため従来どおり（Windowsのclamdはサービス（SYSTEM）で動作し、`SCAN`の権限エラーはほぼ起きない）
- 実機（ClamAV 1.5.4、ホームは0700）: 本リポジトリの251ファイルで0.83秒→0.62秒、1MB超の40ファイル（計約450MB）で1.00秒→0.27秒（いずれもキャッシュが効いた2回目）。194MBのファイルは`INSTREAM`では上限超過のERRORだったが、FILDESでは検査できた（ただしclamdの`MaxFileSize`（既定100MB）を超える部分はclamdの設定どおり検査されない）
