# 非機能要件詳細

対象: アプリケーション全体
前提: 要件定義書には性能要件の記載がなく、要件定義書「保留機能」にCPU使用率制限機能の記載があるのみ。本書はその手前の「初版での動作保証ライン」を定義する。

------------------------------------------------------------------------

## 1. 確認事項の反映結果

| 項目 | 決定内容 |
|---|---|
| 想定スキャン規模 | 一般向けPCを想定し、フルスキャン時数万ファイル規模を基準とする |
| オンデマンドスキャン中のCPU方針 | 他作業を妨げない程度の「バックグラウンドでの平穏な共存」を目安とする（要件定義書の保留機能＝ユーザー設定によるCPU使用率制限とは別に、初版でも既定の配慮を行う） |
| リアルタイム監視時のメモリ目安 | 常時100〜200MB程度を目安とする |

------------------------------------------------------------------------

## 2. 性能要件

### 2.1 スキャン規模の基準値

| 項目 | 基準値 | 備考 |
|---|---|---|
| フルスキャン対象ファイル数 | 数万ファイル（目安5万件） | 一般的な個人PCのCドライブ全体相当を想定 |
| 単一ディレクトリスキャン | 制限なし（フルスキャンの部分集合として扱う） | |
| MULTISCANによる並列度 | clamd側`MaxThreads`設定に依存（本アプリ側では`max_concurrent_connections`＝既定4で接続数を制御、clamdプロトコル設計書5章） | |

### 2.2 スキャン所要時間の目安

- 明確なSLA（秒単位保証）は設けない。ClamAVエンジン自体の処理速度に依存するため、本アプリ側では「進捗が可視化されており、ユーザーが待ち時間を把握できること」を性能要件とする（スキャン画面の進捗バー・件数カウンタ、画面設計書2章に準拠）
- 目安として、5万ファイル規模のフルスキャンが数十分オーダーで完了することを許容範囲とする（実測はテスト仕様書の結合テストで別途検証、8章参照）

### 2.3 オンデマンドスキャン中のCPU使用方針

- clamdプロセス自体のCPU使用（スキャンエンジンの処理）は制御対象外とする（clamd自体の設定領域のため）
- 本アプリ側（GUIプロセス）が行う処理（ファイル列挙、進捗更新、DB書き込み等）については、UIスレッドをブロックしないこと、および過度なポーリング間隔を避けることでバックグラウンド動作時の負荷を抑える
- 具体的な目安：
  - スキャン結果のGUI更新間隔は最短200ms（ファイル単位で毎回再描画せず、一定間隔でまとめて反映する）
  - ファイル列挙処理は`os.walk()`等を用いた逐次処理とし、事前に全件をメモリへロードしない（大規模ディレクトリでのメモリ肥大化・応答遅延を防ぐ）
- 「他作業を妨げない」の具体的な保証手段（プロセス優先度の引き下げ等）はユーザー設定によるCPU使用率制限機能（要件定義書保留機能）で対応する想定とし、初版では上記のGUI側配慮にとどめる

### 2.4 リアルタイム監視時のメモリ使用量目安

| 項目 | 目安値 |
|---|---|
| 常時稼働時（監視のみ、検知なし）のメモリ使用量 | 100〜200MB程度 |
| デバウンスタイマー等の一時的な増加 | max_pending_timers（既定1000件、Windowsリアルタイム監視詳細設計書7章）到達時でも上記目安を大きく超えないこと |

- 上記を超過する場合、Windowsリアルタイム監視詳細設計書7章の`max_pending_timers`の値を見直す、またはデバウンスキューの実装（`threading.Timer`使用数）を軽量な方式（単一スレッドでの時刻管理等）へ変更することを検討する（8章 未確定事項）
- メモリ計測方法：開発時は`tracemalloc`または`psutil`によるプロセスメモリの簡易計測を行い、テスト仕様書のカバレッジ対象には含めないが、リリース前の手動確認チェックリスト（テスト仕様書6章）に測定項目として追加する

### 2.5 起動時間

- タスクトレイ常駐アプリプロセス設計書8章の起動シーケンス（多重起動チェック→config読込→DBマイグレーション確認→GUI初期化）が、通常時（マイグレーションなし）で3秒以内に完了しトレイアイコンが表示されることを目安とする
- DBマイグレーションが発生する場合（DBマイグレーション設計書5.2節）はこの限りではない

## 3. 可用性・信頼性

### 3.1 常駐アプリとしての継続動作

- タスクトレイ常駐アプリとして長時間（数日〜数週間オーダー）起動し続けることを前提とし、メモリリークがないことを目安とする（明確な数値保証はしないが、2.4節の目安値から大きく逸脱しないことをリリース前に確認する）
- リアルタイム監視のデバウンスタイマー、スキャンワーカースレッドプール等、長時間稼働で蓄積しうるリソース（Windowsリアルタイム監視詳細設計書7章）は適切に解放されることを実装時に留意する

### 3.2 clamd未起動時の継続動作

- clamdが起動していない、または途中で停止した場合でも、アプリ本体（GUI・トレイ）はクラッシュせず動作を継続する（エラーコード一覧E1001系のハンドリングに準拠）
- clamd復旧後は自動的に通常動作へ復帰する（次回のPING成功時にホーム画面ステータスが自動更新される）

### 3.3 データ保全

- 隔離ファイル・DB・config.jsonが、通常のアプリ操作（正常終了・異常終了問わず）で破損しないこと
- config.jsonはアトミック書き込み（config.jsonスキーマ定義書2.3節）、DBはSQLiteのトランザクション機構に従う
- 事前バックアップなし自動マイグレーション（DBマイグレーション設計書1章）というトレードオフを許容している点は非機能要件としても明記しておく（既知の制約）

## 4. 動作環境

### 4.1 対象OS・スペック

| 項目 | 内容 |
|---|---|
| OS | Windows 10/11（64bit）、Linux（ArchLinux/KDE環境を主動作確認環境とする） |
| 想定PCスペック | 一般的な個人向けPC（CPU: 近年のミドルレンジ以上、メモリ: 8GB以上を推奨目安とする。2.4節の常駐メモリ目安100〜200MBはこの前提における妥当な比率として設定） |
| 前提ソフトウェア | ClamAVエンジン（clamd/freshclam）が別途インストール済みであること（インストーラ/パッケージング設計書5.3節） |

### 4.2 ディスク容量

- アプリ本体（PyInstaller `--onedir`成果物）：概算100〜200MB程度（Alembic/SQLAlchemy等の依存を含むため。インストーラ/パッケージング設計書8章「未確定事項4」のサイズ最適化検討と連動）
- 隔離ファイル格納領域：検知ファイル数・サイズに依存するため上限を設けない。ただしディスク容量逼迫時の挙動（隔離失敗）はエラーコードE3001でハンドリングする

## 5. セキュリティ（非機能観点）

- SMTPパスワードはOSキーチェーン経由で保存し、config.json・ログ・隔離DBのいずれにも平文で保持しない（config.jsonスキーマ定義書3章）
- 隔離ファイルは読み取り専用・実行不可権限で保存し、誤実行・誤流出のリスクを低減する（テスト仕様書QT-U01）
- ログファイルに個人情報相当（ファイルパス等）が含まれうるため、ログ保持期間（既定90日、config.jsonスキーマ定義書4.8節）を過ぎたログは自動削除する
- ログ・DB・設定ファイルは所有者のみアクセス可とする（マルチユーザー環境での情報漏えい防止、セキュリティレビューで追加。POSIXのみ。Windowsはパーミッションの仕組みが異なり、アプリのフォルダも利用者管理下のため対象外）
  - `logs/`フォルダは0700、ログファイル（`app.log`・ローテーション後の`app.log.<日付>`）は0600（`core/logger.py`。既存の緩い権限のログも起動時に直す）
  - `app.db`は0600（`db/database.py`）、`config.json`は0600（`ConfigService`）、隔離ファイルは0400

------------------------------------------------------------------------

## 6. 運用性・保守性

- ログレベル・保持期間はGUIから変更可能（画面設計書8-6節）
- エラーコード体系（エラーコード一覧・例外設計書）により、サポート対応時の問い合わせ・原因特定を効率化する
- 設定・DBはポータブル構成のため、PC移行時はフォルダごとコピーするだけで環境を再現できる（SMTPパスワードのみ再設定が必要、インストーラ/パッケージング設計書7章）

------------------------------------------------------------------------

## 7. 非対象・スコープ外の非機能要件

以下は要件定義書「保留機能」または本アプリのスコープ外として、初版の非機能要件には含めない。

- ユーザー設定によるCPU使用率上限の明示的な制御（保留機能）
- 多言語対応によるUIの応答性・レイアウト崩れの検証（保留機能、日本語UI固定のため対象外）
- 大規模組織展開を想定した集中管理・監査ログ機能（本アプリは個人PC向け常駐アプリのスコープ）
- ネットワークドライブ・クラウドストレージ同期フォルダに対する性能保証（2.1節の基準値はローカルディスクを前提とする）

------------------------------------------------------------------------

## 8. 未確定事項（次工程で決定が必要）

1. 2.4節のメモリ目安（100〜200MB）を実装完了後にどう計測・検証するか（テスト仕様書6章の手動確認チェックリストへの具体的な測定手順追加が必要）
2. デバウンスタイマー実装（`threading.Timer`を大量生成する現行方式）がメモリ目安を超過した場合の代替実装（単一スレッドでの時刻管理方式等）への切替要否
3. フルスキャン数万ファイル規模での実測値（所要時間・メモリ・CPU）の取得は、テスト環境（テスト仕様書7章 未確定事項1のWindows実機/VM確保）が整い次第、別途性能検証として実施する

## 9. Phase 11 改訂（実測・実装の反映）

- 4.1節 動作確認環境: Windows 11 Pro（Python 3.14/3.15、PySide6 6.12、ClamAV 1.5.4）、Linux（WSL2 Ubuntu 26.04、ClamAV 1.5.4、clamonacc含む）で確認した
- 2.3節 GUI更新間隔: スキャン画面の進捗・件数表示は200ms間隔でまとめて更新する。検知・エラー行の追加は即時
- 2.3節 ファイル列挙: 進捗率（全体件数）を表示するため、対象ファイルを先に列挙してからスキャンする（逐次処理の方針から外れる）。除外ルールは開始時に1回だけ読み込み、ファイルごとにDBを読まない。列挙中も停止できる
- 2.4節 常駐メモリ: Windowsで約134〜157MB（目安100〜200MBの範囲内）
- 2.5節 起動時間: 配布版exeで約1.1〜1.5秒（目安3秒以内）
- 3.2節 clamd未起動時: GUI・トレイはクラッシュせず、ホーム画面・ステータスバー・トレイに「停止」を表示し、サービスとして起動を1回試みる。復旧後は次回の定期確認（60秒以内）で自動的に表示が戻る
- 4.2節 ディスク容量: 配布物の軽量化により展開後約75MB（インストーラ/パッケージング設計書9.1節）
