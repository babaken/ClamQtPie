前提: 要件定義書2章「Windowsサービス化しない／タスクトレイ常駐アプリとして動作」、基本設計書2章 画面遷移（タスクトレイ）

| 項目 | 決定内容 |

## 2. プロセス構成

### 2.1 基本方針

本アプリは**単一プロセス構成**とする。「タスクトレイ常駐アプリ」と「メインウィンドウ」は別プロセスではなく、同一プロセス内でQt（PySide6）のイベントループ上に共存する。

```text
app.py（プロセスエントリポイント）
 │
 ├─ 多重起動チェック（3章）
 │
 ├─ QApplication 起動
 │    ├─ MainWindow（gui/main_window.py） … 通常は非表示 or 表示状態で開始
 │    └─ TrayIcon（gui/tray.py） … 常時表示
 │
 ├─ バックグラウンドサービス群（同一プロセス内、別スレッドで起動）
 │    ├─ RealtimeManager
 │    ├─ SchedulerService（APScheduler）
 │    └─ ClamAVService（都度接続、常駐スレッドは持たない）
 │
 └─ イベントループ（QApplicationのexec()、アプリ終了までブロック）
```

理由：
- 別プロセス構成（トレイ用プロセス＋GUI用プロセス）はIPC実装コストが増える割に、要件定義に「Windowsサービス化しない」程度の制約しかなくメリットが薄い
- Qtは1プロセス内でウィンドウの表示/非表示とトレイアイコンを両立できるため、単一プロセスで要件を満たせる

### 2.2 プロセス終了条件

以下のいずれかでのみプロセス（QApplication）を終了する。

1. トレイメニュー「終了」選択
2. OSからの強制終了シグナル（ログオフ・シャットダウン時のWM_QUERYENDSESSION等、Qtが標準対応）

ウィンドウの「×」ボタン押下、Alt+F4等は**プロセス終了に紐付けない**（4章で詳細）。

## 3. 多重起動防止

### 3.1 実装方式

| OS | 方式 | 詳細 |
|---|---|---|
| Windows | Named Mutex | `CreateMutex(None, False, "Global\\ClamAVFrontend_SingleInstance")`をアプリ起動直後に呼び出す。`GetLastError() == ERROR_ALREADY_EXISTS`の場合は多重起動とみなす |
| Linux | ロックファイル | `~/.local/share/clamav-frontend/app.lock`を`fcntl.flock()`（`LOCK_EX \| LOCK_NB`）で排他ロック。取得失敗時は多重起動とみなす |

### 3.2 多重起動検知時の挙動

- 後発プロセスは、多重起動を検知した時点で以下を行いただちに終了する（exit code 0）
  1. メッセージボックスは表示しない（サイレント終了。タスクトレイアプリとして自動起動される運用が主となるため、ユーザー操作を煩わせない）
  2. ログに「多重起動を検知したため終了しました」をINFOレベルで記録
- **前面化依頼は初版では非対応**（質問時の選択肢どおり、ソケット等のIPCは実装しない）。ユーザーが手動で二重起動した場合、既存プロセスのトレイアイコンから開く必要がある旨をREADME/マニュアルに記載する

### 3.3 ロック解放

- Windows: プロセス終了時にOSが自動的にMutexハンドルを解放する（明示的な解放処理は不要、念のため`CloseHandle()`をfinally相当で実行）
- Linux: プロセス終了時（正常・異常問わず）にOSがファイルディスクリプタを閉じることで`flock`は自動解放される。加えて正常終了時は明示的に`fcntl.flock(fd, LOCK_UN)`とロックファイル削除を行う

## 4. ウィンドウ表示制御（トレイ最小化）

### 4.1 ×ボタン押下時

- `MainWindow.closeEvent(event)`をオーバーライドし、`event.ignore()` + `self.hide()`を実行（ウィンドウを破棄せず非表示化するのみ）
- 初回のトレイ最小化時のみ、トレイアイコンから吹き出し通知（`QSystemTrayIcon.showMessage()`）で「アプリはタスクトレイに常駐しています」を表示する（2回目以降は表示しない。設定でこの案内自体をOFFにできるようにする）

### 4.2 タスクトレイからの表示

- トレイアイコンダブルクリック、または「メイン画面を開く」メニュー選択で`MainWindow.show()` + `raise_()` + `activateWindow()`
- 既に表示中の場合はフォーカスのみ当てる（多重生成しない）

### 4.3 最小化ボタン（_）押下時

- OS標準の最小化動作（タスクバーへ）とする。×ボタンとは挙動を分ける（最小化ボタンはトレイ格納ではなくタスクバー最小化、×ボタンのみトレイ格納という一般的なアプリ挙動に合わせる）

## 5. タスクトレイメニュー（画面設計書9章との対応）

```text
TrayIcon
 ├─ メイン画面を開く   → MainWindow.show()
 ├─ 今すぐスキャン      → クイックスキャンを非同期実行（ScanDispatcherへ投入、完了時に吹き出し通知）
 ├─ 定義更新            → ClamAVService.update_database()を非同期実行
 ├─ リアルタイム監視 ON/OFF（チェック付きメニュー項目、現在状態を反映）
 ├─ ─────────
 └─ 終了                → 5.1参照
```

### 5.1 「終了」選択時のフロー

1. 確認ダイアログ「アプリを終了しますか？リアルタイム監視も停止されます」（はい／いいえ）
2. 「はい」の場合：
   - `RealtimeManager.stop()`
   - `SchedulerService`のジョブスケジューラをシャットダウン（実行中ジョブの中断は待たない。詳細はSchedulerService設計側で規定）
   - ロック解放（3.3節）
   - `QApplication.quit()`

### 5.2 トレイアイコンの状態表現（Windowsリアルタイム監視詳細設計書との連携）

| 状態 | アイコン | 判定条件 |
|---|---|---|
| 通常（監視OFF） | 既定アイコン | `RealtimeManager`未稼働 |
| 監視中 | 監視中アイコン（例: 緑色バッジ） | `RealtimeManager`稼働中 |
| 検知あり（未対応） | 警告アイコン（例: 赤色バッジ） | 直近の検知でGUI未確認の項目が存在する間 |
| clamd未起動/エラー | エラーアイコン | `ClamAVService.ping()`失敗が継続 |

状態の優先順位: エラー > 検知あり(未対応) > 監視中 > 通常

## 6. OS起動時自動起動

### 6.1 Windows

- レジストリキー: `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`
- 値名: `ClamAVFrontend`
- 値データ: 実行ファイルの絶対パス（PyInstaller配布物のexeパス、引数なし）
- 登録/解除タイミング: 設定画面「一般」タブの「OS起動時自動起動」チェックボックスON/OFF時に即時反映（`winreg`モジュールで読み書き）
- 管理者権限は不要（HKCUのため）。ただし本アプリ自体は隔離・検疫等の操作で管理者権限昇格を必要とする場面がある点は別設計（インストーラ/パッケージング設計書）と整合させる

### 6.2 Linux

- `~/.config/autostart/clamav-frontend.desktop`（XDG Autostart仕様）を配置/削除する方式とする（本項はWindows詳細設計の範囲外だが、対称性のため方針のみ記載。詳細はLinux側設計書で別途規定）

## 7. スレッドとGUIの整合性

- `RealtimeManager`・`SchedulerService`はメインGUIスレッドとは別スレッドで稼働させ、GUIへの状態反映はQtのシグナル/スロット機構（`pyqtSignal`/`Signal`）経由で行う（直接のウィジェット操作を別スレッドから行わない）
- トレイメニューの「今すぐスキャン」「定義更新」等の即時実行系も、クリック契機でワーカースレッドへ処理を委譲し、GUIスレッドをブロックしない

------------------------------------------------------------------------

## 8. 起動シーケンス（app.py）

```text
1. 多重起動チェック（3章） → 失敗時はサイレント終了
2. ロック取得成功 → QApplication生成
3. config.json読込（存在しない場合は既定値で新規作成）
4. ロガー初期化（TimedRotatingFileHandler）
5. DatabaseService接続・マイグレーション確認
6. MainWindow生成（config.general.start_minimizedがtrueなら非表示のまま、falseなら表示）
7. TrayIcon生成・表示
8. RealtimeManager初期化（config.realtime.default_enabledに従い自動でstart()するかは既存要件に準拠。ただし監視対象0件の場合は起動しない：Windowsリアルタイム監視詳細設計書3.1節と整合）
9. SchedulerService起動（登録済みジョブをロードして開始）
10. QApplication.exec() でイベントループ開始
```

### 8.1 config.json 追加項目

```json
{
  "general": {
    "start_minimized": true,
    "show_tray_hint_shown": false
  }
}
```

## 10. Phase 11 改訂（実装で確定した仕様）

- 3.1節 Linuxのロックファイル: 本書どおり`~/.local/share/clamav-frontend/app.lock`（`XDG_DATA_HOME`があれば従う）とした（実装がアプリのフォルダに置いていたのを修正）
- 3.2節 多重起動検知時: ロガー初期化前のため、ログファイルへ「多重起動を検知したため終了しました」をINFOで直接追記してから終了する。管理者権限で起動中のインスタンスのmutexに通常権限からアクセスしてアクセス拒否になった場合も「起動済み」とみなす
- 3.2節「プロセス間通信は実装しない」の例外: 通知（Toast）のクリックで隔離画面を開くため、ユーザー単位のフォルダ（`%LOCALAPPDATA%\clamav-frontend`）の依頼ファイル1つだけを受け渡す（起動中のアプリがQFileSystemWatcherで監視）。ソケット等のIPCは引き続き使わない（通知機能詳細仕様書9章）
- 4.1節: トレイ格納時の案内は設定画面「×ボタンでトレイに格納したときに案内を表示」でON/OFFできる（ONにして保存すると次回の×ボタンで再び案内する）
- 5章「今すぐスキャン」: 画面を開かずにクイックスキャン（9章 未確定事項1→対象はデスクトップ・ダウンロード・ドキュメント・一時フォルダ、Windowsはスタートアップフォルダも）を実行し、開始時と完了時に吹き出し通知する。実行中は「スキャンは既に実行中です」と通知する
- 5章「リアルタイム監視 ON/OFF」: OFFにする時は確認ダイアログを表示する（ホーム画面と共通）
- 5.2節 トレイアイコンの状態: 状態はホーム画面のカード・ステータスバーと同じ定期確認から更新する（clamd 60秒ごと、監視ON/OFF 2秒ごと）。「エラー」はclamdのPING失敗時、「検知あり」はリアルタイム監視・スケジュールスキャンの検知で表示し、利用者が隔離画面を開いた時点で解除する
- アイコン素材: ClamAV公式ロゴは商標のため使わず、オリジナル図案を`scripts/generate_icons.py`で生成する（盾の中の二枚貝＋弾かれるウイルス、状態は右下のバッジ）。素材が無い場合はQt標準アイコンで代替する（空のアイコンだとWindowsではトレイに表示されず操作不能になるため）
- 6章 自動起動: 設定画面で保存した時点で即時反映し、失敗時はE8002を表示してチェックと設定値を元に戻す。開発時（python app.py）は`python.exe "app.py"`を登録する
- clamdの起動: 停止を検知したらサービスとして1回起動を試みる（clamdソケット通信プロトコル設計書9.5節）
- 9章 未確定事項2（終了時の実行中ジョブ）: 待たずにスケジューラを停止する（`shutdown(wait=False)`、5.1節どおり）
- 9章 未確定事項3（Linux固有の設計）: 多重起動防止・自動起動（XDG Autostart）は本書の方針で実装済み。リアルタイム監視は「Linuxリアルタイム監視詳細設計書」を作成した

## 11. 段階 12 改訂（v0.10.0: サービス化）

v0.10.0 で、2.1 節の「単一プロセス構成（トレイ・画面・監視・スケジュールが同じプロセス）」をやめ、保護の処理をサービスに移した。トレイGUI（`tray_main.py`）は一般の利用者の権限で動くサービスのクライアントになった。前提の「Windowsサービス化しない」（要件定義書2章）は、この版で改めた。1〜10 章のうち、プロセス構成（2 章）・多重起動防止（3 章）・「終了」のフロー（5.1 節）・起動シーケンス（8 章）は、この章が優先する。ウィンドウの表示制御（4 章）・メニューの並び（5 章）・アイコンの状態（5.2 節）は、11.4 節の変更を除いて引き続き有効。実装の記録は `clamav_frontend/README_DEV.md` の §65〜§69・§72・§75。

### 11.1 プロセス構成（2 章の置き換え）

```text
tray_main.py（トレイGUI のプロセス。利用者ごと、サインインのセッションごとに 1 つ）
 │
 ├─ 多重起動チェック（11.2 節）
 ├─ QApplication 起動（最後のウィンドウを閉じても終了しない）
 │    ├─ TrayIcon（常に表示）
 │    └─ MainWindow（サービスにつながってから作る）
 ├─ ApiClient（サービスの内部 API。要求は QtNetwork で非同期に送る）
 ├─ EventStream（サービスのイベント（SSE）を受け取り、画面を読み直す）
 └─ イベントループ

サービス（別のプロセス。LocalSystem / root）
 └─ リアルタイム監視・スケジュール・スキャン・定義更新・隔離・通知の保存
```

- トレイGUI は、監視・スケジュール・DB を自分では持たない。画面はサービスと同じ形のプロキシ（`api_client/proxies.py`）を通して内部 API を呼ぶ
- 接続先は、サービスが書く `endpoint.json` のポート（無ければ設定の既定値）。トークン（`user.token`）を送る前に、毎回そのポートで待ち受けているのがサービスかを確かめる
- 管理者の操作は、昇格ヘルパー（`elevate_main.py`）を UAC（Linux は pkexec）で起動して頼む。トレイGUI は管理者のトークンを持たない
- サービスにつながらない間は、トレイのアイコンをエラーの状態にして 5 秒ごとにつなぎ直す。つながったら画面を作る（それまでメイン画面は開けない）。版数（API の版）が合わないときも同じ
- トークンを読めない（グループに入っていない）ときは、`clamqtpie-ctl users add <利用者>` を案内して終わる（E8110）。グループに入れた直後でサインインし直していないときは、サインインし直す（Linux で効かなければ PC を再起動する）よう案内する

### 11.2 多重起動防止（3 章の置き換え）

| OS | 方式 |
|---|---|
| Windows | Named Mutex `Local\ClamQtPie_Tray`（サインインのセッションごと。同じ PC でも、別の利用者のトレイGUI は動ける） |
| Linux | 利用者ごとのロックファイル `~/.local/share/clamqtpie/app.lock`（`XDG_DATA_HOME` に従う） |

- 多重起動を検知したら、ログに残してすぐに終わる（3.2 節と同じ）
- サービスの二重起動の防止は SCM・systemd に任せる（開発中の `--console` は、データの置き場所のロックで防ぐ）

### 11.3 起動シーケンス（8 章の置き換え）

```text
1. ログの初期化（利用者ごとの場所: %LOCALAPPDATA%\clamqtpie\logs、~/.local/share/clamqtpie/logs）
2. 多重起動チェック → 既に動いていれば終了
3. QApplication 生成、テーマの適用
4. 旧版の自動起動の登録を、このトレイGUI で登録し直す（登録されていた場合だけ）。通知のクリックの URL スキームを登録し直す（Windows）
5. TrayIcon を表示
6. サービスにつなぐ（11.1 節）。つながらなければ、つながるまで待つ
7. つながったら、MainWindow と 10 画面を作り、プロキシをつなぐ。gui.json の start_minimized が false なら表示する
8. サービスの未読の通知を読み、デスクトップに出す（11.5 節）
9. QApplication.exec()
```

- 8.1 節の `general`（`start_minimized`・`show_tray_hint_shown` など）は、サービスの `config.json` から利用者ごとの `gui.json`（`%APPDATA%\ClamQtPie\`・`~/.config/clamqtpie/`）に移した
- 8 章の 3・5・8・9（config.json の読み込み、DB、リアルタイム監視、スケジューラ）はサービスが行う

### 11.4 「終了」・メニュー（5 章・5.1 節の変更）

- 「終了」はトレイGUI だけを終わらせる。サービスの監視・スケジュールは続くため、5.1 節の確認ダイアログ（「リアルタイム監視も停止されます」）と、監視・スケジューラの停止はやめた
- 保存していない変更がある画面（リアルタイム保護・スケジュール）を離れる・ウィンドウを閉じるときは、「保存」「破棄」「キャンセル」を確かめる。トレイの「終了」では確かめない
- メニューに「未読の通知（n 件）」と「WebUI」のサブメニューを足した（画面設計書 12 章）
- 「今すぐスキャン」は、その利用者のフォルダの中のクイックスキャンを、利用者の権限（user のトークン）のまま頼む。フルスキャン・ほかの場所は、昇格して頼む
- 「リアルタイム監視 ON/OFF」は管理者の操作のため、昇格ヘルパーの確認を経る
- アイコンの状態（5.2 節）: 「エラー」に、サービスにつながらないときを加えた。ツールチップに未読の通知の件数を出す

### 11.5 通知（デスクトップへの表示）

- サービスはデスクトップに通知を出せない（Windows はセッション 0、Linux はサインインした利用者のセッションが無い）ため、通知を DB に未読として保存する。トレイGUI がそれを読み、この利用者のデスクトップに出す（通知機能詳細仕様書と README_DEV §59・§67）
- つながったとき（起動時・つなぎ直したとき）にまだ出していない未読が 2 件以上なら、「未読の通知が n 件あります」の 1 件にまとめる。動いている間は `notification` イベントで 1 件ずつ出す
- 既読にしたもの（ほかのトレイGUI・WebUI で既読にしたものも含む）は、通知センターから消す

### 11.6 サービスの変更の反映（7 章の変更）

- 監視・スケジュールのスレッドはサービスにあるため、7 章のシグナルによる画面への反映は、サービスのイベント（SSE）による反映に置き換えた。主なイベント: `status`（2 秒ごとの稼働状態）、`config.changed`、`scan.*`・`update.*`（進み具合）、`schedule.finished`、`notification`・`notification.acked`、`data.changed`（一覧の変更。ほかのトレイGUI・WebUI で変えたものも、開いている画面に出す）
- イベントを受け取れなかった間（つなぎ直しの途中など）の変更は、画面を開いたときにも読み直して出す

### 11.7 OS 起動時の自動起動（6 章の変更）

- 6.1 節の値の名前は `ClamQtPie`（旧名 `ClamAVFrontend` は起動時に引き継ぐ）。値はトレイGUI（`ClamQtPie.exe`）のパスで、`Program Files` の空白のため引用符で囲む
- Windows のインストーラは、「サインインしたときにトレイGUI を起動する」を選べる（インストーラ/パッケージング設計書 10.3 節）
- 6.2 節の Linux は `~/.config/autostart/clamqtpie.desktop`
- サービスは OS が起動する（Windows は通常の自動起動、Linux は systemd の `enable`）。サインインしていなくても保護は続く
